## [0:00–0:20] 开场定位

各位老师好。三分钟，我讲三件事：一套只有五个后端依赖的架构，一条断网也能用的三段式降级链路，一条真下发、真回执的指令闭环。稿子里的数字都出自我们自己的项目审计报告。

**若被打断的追问与应答**
- 问：三分钟够讲吗？ 答：够。只讲三个点，其余留给你们追问。

## [0:20–1:10] 架构与依赖克制

先说为什么后端只用五个依赖。它们是 FastAPI、Uvicorn、paho-mqtt、httpx、pydantic，版本全部锁死。没有 SQLAlchemy，没有 requests，没有 OpenAI SDK，没有任何 MQTT 高级封装；数据库直接用 Python 标准库的 sqlite3，前端只装 Vue 和 ECharts 两个运行时依赖，请求用原生 fetch 发。这套依赖清单是审计时用 git ls-files 逐条核出来的，不是我们自述的。
这不是图省事，是每一层都攥在自己手里：MQTT 收发、WAL、超时重试全是我们自己写的，出问题一眼能定位。代价也实测过：生产三个容器，合计常驻不到一百兆内存，宿主是一台 1.7G 内存的 2 核机器，负载长期在零点一上下，开了 4G swap 基本没动用。2C2G 的约束下我们留足了余量。

**若被打断的追问与应答**
- 问：不用 ORM 不怕写错 SQL？ 答：八张表、七个索引都写在 db.py 的 DDL 里，幂等建表，开 WAL，写入单例加锁、读取线程本地连接。
- 问：依赖少能证明什么？ 答：证明没有一层是我们讲不清的黑盒——审计报告能指到每个端点在第几行。
- 问：具体占多少内存？ 答：截至 2026-11-04 实测，backend 58.1 MiB、simulator 19.6 MiB、mosquitto 3.3 MiB，合计约 81 MiB；这个数在 80 到 95 MiB 之间波动。

## [1:10–2:00] 三段式降级

第二件事。农业现场网络极差，所以降级不是补丁，是主设计。推演链路分三段：第一段 primary 走真实大模型；第二段做交叉校验，判据只有一行，偏差等于模型减产率减先验减产率的绝对值，超过十五个百分点就判模型跑偏，改用先验值并打上 corrected 标记；第三段 fallback，没 Key、超时、返回非 JSON，一律落到本地农学规则库。四条外部调用路径——chat、complete_json、discover_models、probe——永远不会冒泡异常，永远返回 HTTP 200。
这是实测过的：生产环境没配 Key，直接打推演接口，返回 200，source 是 fallback，model 是 local-agronomy-rules，degraded 为 true，照样产出完整的三节点推演树和三步白盒。全仓十四条 except Exception 里十三条带 noqa、八条还写了中文理由，那是设计，不是疏漏。每次推演的 prompt 平均 2184 字符、result 平均 2912 字符，全部落库可溯源。

**若被打断的追问与应答**
- 问：降级之后结论还准吗？ 答：降级走的是后端农学规则库，和交叉校验用的是同一套先验，口径一致。
- 问：大模型真能用吗？ 答：真实大模型的成功路径本次审计没有复跑，我们只声称降级路径实测通过。
- 问：为什么不是每条 except 都写理由？ 答：十三条带 noqa，其中八条写了中文理由；剩下五条是「关闭时忽略异常」这类自解释场景。唯一没有 noqa 的是 db.py 的健康探活，异常就返回 False，本身不需要标注。

## [2:00–2:45] 指令真闭环

第三件事，指令闭环。我下发一条灌溉指令：地块 A，设备 FJ-CITRUS-A02，时长三十分钟。接口马上返回 200，status 是 dispatched，topic 是 agri/command/A/FJ-CITRUS-A02，QoS1 下行。回执在同一秒内就回来了，status 变成 executed，ack_at 是 2026-11-02T20:15:52，detail 写着模拟器已执行并回执。
再看数据：这台设备的土壤墒情从指令前的 51.2 单调回升到 71.4，中间是 56.7、60.5、64.0、68.8；同一个窗口里，A01、B01、B02 三台的中位数分别只动了负 0.9、正 2.1、正 1.0。这说明两件事：它真的改了设备端的采样值，不是弹了个提示；而且它只作用于目标设备。模拟器日志能逐条对上：收到指令、执行结果 ok 为 true、已回执 status 为 executed、qos 为 1。换句话说，屏幕上那个绿灯背后，是数据库里一条真记录，和 MQTT 上一条真回执。状态机是 dispatched 到 executed、failed 或 timeout，超时清扫跑在应用内的 asyncio 任务里，不新增常驻进程。

**若被打断的追问与应答**
- 问：会不会是前端自己改的数？ 答：数据是从 telemetry 表里查出来的，当天那张表有十五万行，前端只负责画。
- 问：怎么保证不是广播？ 答：同窗口另外三台设备墒情中位数几乎不动，目标设备涨了二十个点，这就是定向性证明。
- 问：起点为什么不是 30.5？ 答：30.5 是模拟器按 12% 概率注入的越界脏样本，用来验证告警链路；把它当真实起点会自相矛盾。剔掉注入样本后，指令前的中位数是 51.2。

## [2:45–3:00] 收尾

收个尾。这套系统跑在 2C2G 上只吃不到一百兆内存，三个容器零重启，后端健康检查 healthy，MQTT 链路 connected 为 true；公网直连最慢一条接口一百三十五毫秒，服务器内回环全部低于三十二毫秒，二十四小时的聚合统计扫了近七万个采样点，公网一百一十四毫秒。库里遥测的时间跨度是七十六小时，十五万条数据写进来，三个容器一次都没重启。网络断了它不白屏，指令发出去它真有回执。谢谢各位。

**若被打断的追问与应答**
- 问：做过并发压测和长跑吗？ 答：没有，审计报告已列为未验证，我们不吹。
- 问：为什么只报速率不报总行数？ 答：遥测是每小时 2880 条往里写的，总行数每天都在变，报速率才是可复核的；要具体数字我按截至 2026-11-04 给你。
