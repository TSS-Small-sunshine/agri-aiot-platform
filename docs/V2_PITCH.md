## 一、主问题：减产 20% 是怎么算的

### 评委问

> 「你推演树上的**减产 20%** 是怎么算的？是不是随便编一个数？」

### 一句话总纲（先立住，再展开）

> **「这个数不是编的，它是基于『传感数据 + 大模型上下文推理』的**概率预估**。
>  它的每一个输入都能在界面上点开看到：原始样本条数、命中的农学规则、以及发给大模型的完整 Prompt。」

### 四层递进（可直接照读，约 60~80 秒）

**第一层：数据来源真实。**

「减产结论的输入不是随机数，而是**本地 SQLite 里该地块最近 10 分钟的真实遥测样本**——
气温、湿度、土壤墒情、土壤温度、电量五项，还包含**样本条数和设备编号**。
这套系统的数据从 MQTT 进来、落库到 SQLite，推演时现查现用，不缓存、不编造。
界面上那个『展开推演逻辑』面板的第一行，写的就是『读取 A区柑橘园 最近 10 分钟遥测，共 N 条样本（设备 …）』——
这个 N 是真实的查询结果，评委可以现场核对。」

**第二层：规则可追溯。**

「我们写了一个**完全独立于大模型的农学先验引擎**（`backend/app/knowledge.py`），
它只用本地规则和冻结口径算结论，不访问网络、不访问数据库，是纯函数。
它命中了哪条规则、为什么命中、没命中哪些规则，全部写进白盒时间轴——
前端点『展开推演逻辑』就能现场展开给评委看。
先验口径有两条，都是写死在代码里的常量：
一是**亩均滴灌耗电 0.15 kWh/亩**；二是**水分胁迫减产按『缺水深度 × 持续时间』在 15%~25% 区间插值**。
深度因子 = 墒情跌破正常下限多少、除以（正常下限 − 严重下限）；
持续因子 = 墒情连续低于下限多少小时、除以 24 小时；两个因子各占一半权重。
所以没有水分胁迫时，减产就是 **0**——我们不虚报风险。」

**第三层：大模型是推理层，不是造数层。**

「`backend/app/reasoning.py` 把上面那些结构化上下文组装成 Prompt，
Prompt 里内联了 JSON Schema，**约束模型只能在这个结构里填数**；
模型返回后我们还要做**交叉校验**：如果模型给的减产率和后端先验算出来的值
**偏差超过 15 个百分点**（`REASONING_PRIOR_TOLERANCE_PCT`），我们就判定模型这一次不可信，
**以后端先验为准**，并在白盒里明确标注『已用农学先验模型校正』。
也就是说，大模型可以提出观点，但最终数字要过我们自己那道关。」

**第四层：它是概率预估，不是承诺。**

「所以我从来不说『这块地一定减产 20%』，我说的是『按当前墒情趋势与持续时间，
减产风险落在 15%~25% 这个区间里，当前估算 20%』。
它的用途是**给干预排序**——先救哪块地、先开哪台阀——不是精确产量预测。
如果评委需要，我们可以现场把这块地的原始样本条数、命中规则和模型的原始返回一起展开。」

### 追问兜底（如果评委继续追）

> 「您可能想问：这个 20% 到底准不准？我的回答是——**它的绝对值不追求精确，它的排序必须可靠**。
>  因为『缺水更深、持续更久 → 减产更大』这个单调关系是农学常识，我们把它写成了可验证的插值函数，
>  而不是让大模型自由发挥。真要落地到生产，我们需要的是**田块级的实测产量回归**去标定这两个系数，
>  现在的 15%~25% 是行业常见的胁迫损失区间，作为**演示系统的先验口径**是站得住的。」

## 二、追问与应答（10 问）

### Q1｜你这套系统离开大模型还能用吗？

「能，而且是**刻意设计的**。推演接口是**三段式降级**：

1. 大模型返回合法 JSON 且通过 Schema 校验 → `source="primary"`，界面上打【主模型生成】；
2. 大模型数字与先验模型偏差 > 15 个百分点 → 以后端先验为准，`corrected=true`，界面上打【主模型生成·已校正】；
3. 无 Key / 超时 / 返回非 JSON / Schema 校验失败 → 由本地农学先验引擎产出**同结构**的 JSON，
   `source="fallback"`、`model="local-agronomy-rules"`，界面上打【离线降级策略】。

三条路径产出的 JSON 结构完全一致，前端**同一套渲染代码**。
铁律是：**任何异常都收敛为降级结果，绝不冒泡成 5xx**。
换句话说，就算比赛现场断网、Key 过期、服务商限流，推演树照样会长出来，只是角标从『主模型』变成『离线降级』。」

### Q2｜大模型返回非 JSON 或者超时怎么办？

「两层保险。
**第一层**，我们在 Prompt 里内联了 JSON Schema，并且用 `response_format={"type":"json_object"}` 强制它输出 JSON 对象；
推演单独给了 **45 秒**超时（`REASONING_TIMEOUT_SECONDS`），比农技问答的 20 秒宽，因为推演的 Prompt 更长。
**第二层**，拿到文本后立刻 `json.loads` + Pydantic 模型校验，任何一步失败都会被捕获，
把失败原因写进 `error` 字段（例如『大模型返回无法通过 Schema 校验：ValidationError: …』），
然后走降级路径。
所以评委永远看到的是一个 200 响应加一条说明，而不是一个报错弹窗。」

### Q3｜数据是模拟的，那推演还有意义吗？

「有意义，因为**我们模拟的是数据，不是推理链**。
数据源可以替换：现在传感器数据由 MQTT 模拟器产生，但整条链路——MQTT 订阅、SQLite 落库、
窗口聚合、规则匹配、Prompt 组装、交叉校验、指令下发与回执——**一行都不用改**，
换成真实传感器只是把 `MQTT_HOST` 指向真 broker、把设备清单换成真设备码。
反过来说，如果推理链本身是假的，那换成真数据也没用。
我们这次演示想证明的恰恰是**推理链是通的**：
同一套代码，喂真数据就出真结论。」

### Q4｜0.15 kWh/亩 和 15%~25% 这两个数从哪来？

「它们是**冻结在代码常量里的先验口径**，不是从数据里学出来的——这一点我不遮掩。
`POWER_KWH_PER_MU = 0.15`：柑橘园滴灌常用 15~20 立方/亩的灌水定额，
按常见的水泵功率与扬程折算到每亩约 0.15 度电，属于工程估算量级；
`YIELD_LOSS_MIN_PCT = 15.0`、`YIELD_LOSS_MAX_PCT = 25.0`：
这是柑橘遭受**明显水分胁迫**时常见的减产区间，我们把『缺水深度』和『持续时间』
各按 50% 权重插值到这个区间里。
我强调两点：第一，**这两个数在代码里是常量，评委可以当场查**；
第二，**没有胁迫时减产恒为 0**，我们不会为了画面好看虚报风险。
真要做生产系统，这两个系数必须用田块实测数据重新标定——这在我们的路线图里。」

### Q5｜为什么用 SQLite 不用 MySQL？

「因为目标机器是**2 核 2G**，而且这是一个单机演示系统。
第一，内存：MySQL 光常驻就要几百 MB，我们三容器加起来才几十 MB；
第二，并发模型够用：我们开了 **WAL**（`PRAGMA journal_mode=WAL`），读写不互锁，
写入走一个全局连接加一把 `threading.RLock`（MQTT 线程和 HTTP 线程共用），读取走 `threading.local` 独立连接；
对 4 台设备、5 秒一条的写入频率来说，这个并发能力绰绰有余。
第三，运维成本：SQLite 是单文件，备份就是拷一个文件，**零运维**。
在 2G 内存的机器上，省下来的每一 MB 都是留给业务的。」

### Q6｜2 核 2G 真的跑得动吗？

「跑得动，而且我们**在真机上量过**。
目标机型（阿里云轻量 2C2G）总内存 1735MB，三个容器——mosquitto、backend、simulator——
**合计常驻约 94MiB**；这台机器还自带 4GB swap，`vm.swappiness=20`。
更关键的是我们**不在服务器上构建**：镜像由 GitHub Actions 构建推送到 ghcr.io，
服务器只执行 `docker compose pull && docker compose up -d`。
为什么这么设计？因为我们踩过坑——在 2G 机器上构建前端时，
Vite 生产构建单进程就吃到 1.4GB，直接被 OOM Killer 杀掉（`exit code 137`）。
这件事我们写进了 CHANGELOG 的『难点一』，包括量化前后对比：
构建峰值内存 1.8GB → 380MB，后端镜像 1.1GB → 210MB。」

### Q7｜你说的指令闭环是真的闭环，还是前端弹个 Toast？

「是真闭环，链路是**四跳**，每一跳都能在数据库里查到：

1. 前端（或接口）调 `POST /api/command/execute`，后端把指令**落库**为 `status=dispatched`；
2. 后端向 `agri/command/{plot}/{device}` 发布 MQTT 报文，**QoS 1**；
3. 模拟器订阅到这个主题，调 `apply_command()` **真实改变后续采样数值**——
   开滴灌会把墒情回升速率设为 0.85%/秒并持续指定分钟数，所以下一轮遥测里墒情**真的会回升**；
4. 模拟器向 `agri/command_ack/{plot}/{device}` 回执，后端把状态改成 `executed` 并记录 `ack_at`。

如果 30 秒（`COMMAND_ACK_TIMEOUT_SECONDS`）内没收到回执，后台的扫描任务会把它标成 `timeout`。
所以指令历史里有四种状态：`dispatched` / `executed` / `failed` / `timeout`，
每种都有对应的中文说明。**弹 Toast 是没有回执、没有状态机的**——这是最直观的区别。」

### Q8｜农资 SKU 是不是硬广？

「不是广告，是**商业闭环的演示**。
推演树的每个处置节点上都带一组 `sku_keywords`，比如缺水胁迫的处置节点带 `["滴灌带","抗旱保水剂"]`；
前端拿这组关键词去 `GET /api/shop/skus?keyword=` 查，命中的 SKU 就挂在结论下面。
逻辑是『**诊断 → 处置 → 需要的物资**』，把决策闭环延伸到采购闭环。
数据是 6 条 Mock 记录，启动时幂等 seed，**用户可以自己增删改**；
图片字段只存一个标识符，前端用本地占位块渲染，**不依赖任何外网图片**——
这既是为了离线演示，也是为了避免版权问题。」

### Q9｜为什么不用 vue-router，也不用 UI 框架？

「因为我们有**禁止臃肿依赖**的硬约束，而且这里确实用不上。
整个前端只有 3 个路由：`/`（主大屏）、`/legacy`（V1 大屏）、`/mobile`（移动端）。
为此引入 vue-router 要多约 20KB 和一个依赖，而我们手写一个基于 `history.pushState` + `popstate`
的极简路由只有 30 行（`frontend/src/router.js`），未命中的路径一律回落 `/`。
UI 框架更没必要——我们只有 3 个弹层和 1 个 Toast，自己写反而更好控制深色主题的一致性。
依赖越少，构建峰值内存越低，这跟『2G 机器上构建会 OOM』那个坑是同一个道理。」

### Q10｜大屏白屏 / 深链打不开是怎么解决的？

「这个问题我们踩得很深，值得单独讲。现象是：访问一个不存在的深链 `/nope/deep`，
**整页白屏**，控制台报 `Failed to load module script: Expected a JavaScript-or-Wasm module script
but the server responded with a MIME type of "text/html"`。
根因是：`index.html` 用的是**相对路径** `./assets/*.js`（Vite `base: "./"`），
在深链下浏览器把它解析成 `/nope/assets/*.js`；而 SPA 回退会把**任意未知路径**都返回 `index.html`，
于是浏览器拿到一个 `content-type: text/html` 的『JS 文件』，按 MIME 校验直接拒绝执行——脚本从未运行，所以白屏。
我们的解法是两步：
第一，后端区分**资源类请求**（`/assets/**` 或带资源扩展名的路径），这类请求**不回退**，直接返回真 404；
第二，回退 `index.html` 时**在响应体里注入一个 `<base>` 标签**指向应用根，
让相对路径重新解析到 `/assets/**`——注意是**运行时注入响应体**，不改磁盘上的构建产物。
这里有个中间结论要强调：**只做『资源类请求 404』并不充分**，
因为根路径 `/` 下的相对引用仍然是对的、深链下仍然是错的，必须配合 `<base>` 注入才彻底。
效果：`/nope/deep` 由 `#app` 零子节点变成正常渲染，控制台零报错。」

## 三、现场演示脚本（8 步）

> 全程约 3 分钟。**每一步都先做、再讲**，不要边做边讲。
> 括号里是预期现象，看不到就按第四节的兜底话术走。

### 第 1 步：确认服务活着

```bash
curl -s http://127.0.0.1:8000/api/health
```

**预期**：`"status":"ok"`、`"db":{"ok":true}`、`"mqtt":{"connected":true}`。
**讲解点**：一个接口同时报出数据库、MQTT 和大模型三个依赖的状态——这就是我们的可观测性底线。

### 第 2 步：打开大屏，展示 KPI 与实时曲线

浏览器打开 `http://<服务器IP>:8000`。

**预期**：顶栏三个 KPI（在线设备 4 / 平均墒情 / 未确认告警）、后端与 MQTT 状态胶囊、温湿度曲线在动。
**讲解点**：5 秒轮询，前后端同源同端口，对外只有 8000 一个端口、一条安全组规则。

### 第 3 步：点开齿轮，演示「配置中心热生效」

点右上角齿轮 → 填 Base URL / API Key → 点模型下拉（列表来自 `GET /api/models`）→ 保存。

**预期**：保存后无需重启容器，界面上的模型名立刻变成你选的那个，角标从【离线降级策略】变成【主模型生成】。
**讲解点**：**这是 V2 最实用的一点**——评委可以现场把自己的 Key 填进去，
不用改服务器代码、不用重启容器，配置优先级是 `runtime_config.json` > 环境变量 > 内置 Mock。
**注意**：如果现场没网，这一步跳过，直接讲『不填也能跑，走降级』。

### 第 4 步：发起一次推演，展示因果树

在推演面板点「模拟推演」（或 `curl -X POST .../api/reasoning/simulate -d '{"plot_code":"A"}'`）。

**预期**：长出一棵三节点因果树——根节点（当前数据）→ 风险节点（减产风险 X%）→ 处置节点（开启滴灌 N 分钟）。
**讲解点**：减产率不是拍的，是「传感窗口 + 农学先验 + 大模型推理」三段拼出来的。

### 第 5 步：展开白盒，这是全场最有说服力的一步

点处置节点上的「展开推演逻辑」。

**预期**：三步时间轴——① 环境数据读取（**真实样本条数 + 设备编号 + 五项指标实测值**）；
② 匹配农学规则（**命中哪条、没命中哪些，逐条列出**）；③ 大模型结论生成（**含与先验模型的偏差说明**）。
**讲解点**：把这句话说慢一点——「评委可以数一下这里的样本条数，
它是这条地块最近 10 分钟真实入库的遥测条数，不是我们写死的。」
如果时间允许，再点开 `GET /api/reasoning/{id}` 展示**完整 Prompt 原文**（实测约 2.2K 字符（UTF-8 约 3.0 KB，随上下文略有浮动））。

### 第 6 步：下发一条指令，证明闭环是真的

在处置节点上点「执行」（下发 `irrigation_on`）。

**预期**：指令状态从 `dispatched` 变成 `executed`，`ack_at` 有时间戳；
**紧接着看墒情曲线——几十秒内真的回升**。
**讲解点**：模拟器收到 MQTT 指令后**真的改了后续采样数值**，所以曲线会动。
这不是前端动画，是数据库里多出来的采样点。

### 第 7 步：展示 SKU 挂载（商业闭环）

在处置结论下面看关联农资卡片。

**预期**：按 `sku_keywords` 命中的 SKU 列表（如滴灌带、抗旱保水剂），含价格、规格、库存。
**讲解点**：诊断 → 处置 → 物资，决策闭环延伸到采购闭环；图片是本地占位块，不依赖外网。

### 第 8 步：收尾——展示大字模式与移动端

点顶栏「大字模式」开关；再把浏览器窗口缩窄或直接访问 `/mobile`。

**预期**：大字模式下字号整体放大、对比度提高；`/mobile` 是一套单手可操作的移动端布局。
**讲解点**：这套系统不止是给评委看的，也是**给田间的人用的**——
棚里光线强、手机小，所以有大字模式和移动端。
最后补一句：`/legacy` 保留了 V1 的大屏，老用户的操作习惯不会被破坏。

## 四、可能翻车的现场风险与兜底话术

### 风险 1｜现场没有外网 / 大模型 Key 不可用

**现象**：配置中心填了 Key 但探活失败；或推演角标一直显示【离线降级策略】。

**兜底**：「这说明我们的降级设计生效了。
这套系统从第一天就假设大模型是**整条链路里最不可控的一环**，
所以我们对它的态度是『可以慢，但不能拖垮别人』——
任何异常都降级成本地农学先验引擎的结果，HTTP 仍然返回 200。
**没有 Key，今天的演示一步都不会少。**」

**动作**：不要现场排障。直接继续讲降级路径，把事故变成亮点。

### 风险 2｜8000 端口没放行 / 外网打不开

**现象**：浏览器转圈或连接被拒绝。

**兜底**：「阿里云的安全组是独立于服务器的一道墙，我先把演示切到本机。」

**动作**：立刻在本机跑 `docker compose up -d`（或 `scripts/dev_up.ps1`），用 `http://127.0.0.1:8000` 继续。
**赛后**：去阿里云控制台给实例的安全组加一条「入方向 8000/TCP 允许」。

### 风险 3｜大屏白屏

**现象**：页面打开是空白的，F12 有 MIME 或 404 报错。

**兜底**：「这是前端产物没打进镜像的典型症状，我换个入口。」

**动作**（按顺序试，不要卡住）：

1. 先访问 `http://<IP>:8000/legacy` —— V1 大屏走的是另一套组件，往往还能渲染；
2. 还不行就 `curl -s http://127.0.0.1:8000/ | head -c 200`，
   如果返回的是一行 JSON（而不是 HTML），说明静态目录是空的，**前端产物没进镜像**；
3. 这时切到本机演示，并顺势讲 CHANGELOG 的「难点二：跨域与 SPA 404」——
   我们正是用**同源托管 + SPA 回退 + `<base>` 注入**解决这类问题的。

### 风险 4｜模拟器没数据，曲线是平的 / 设备全灰

**现象**：KPI 显示在线设备 0，曲线不动。

**兜底**：「模拟器还在重连，我们先看已有数据。」

**动作**：`docker compose logs --tail=20 simulator` 看是否在发布；
确认 `.env` 里 `MQTT_HOST=mosquitto`；
再不行就 `docker compose exec -T backend python - --hours 24 --step-minutes 5 < scripts/seed_history.py`
灌 24 小时历史数据，**曲线立刻就有了**。

### 风险 5｜评委追问「数据都是模拟的，凭什么算落地」

**兜底**：「对，传感器是模拟的——但**整条链路是真的**：真 MQTT、真 SQLite、真规则引擎、
真 HTTP 调用、真指令闭环。换成真实设备只需要改两个环境变量（`MQTT_HOST`、`SIM_DEVICES`），
代码一行不动。我们把有限的答辩时间花在了**决策链**上，而不是花在采购硬件上。
如果评委想看真实数据，我现在就可以把 `MQTT_HOST` 指到你们现场的 broker。」
